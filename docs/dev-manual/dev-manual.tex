\section{System Architecture}
The application uses a three-layer architecture:
\begin{verbatim}
tkinter frontend -> FastAPI backend -> PostgreSQL 16
\end{verbatim}
The frontend communicates with the backend using HTTP and the \texttt{X-API-Key} header. Database access is handled by \texttt{psycopg}. PostgreSQL is started with Docker Compose for local development.

Important repository areas are:
\begin{verbatim}
api/                    FastAPI application and tests
db/                     PostgreSQL schema and seed data
frontend/chess_club_fe/ tkinter frontend
frontend/debian/        Debian package files
docs/                   proposal and manuals
scripts/                local helper scripts
.github/workflows/      GitHub Actions CI
\end{verbatim}

\section{Database Model}
The schema in \texttt{db/01\_schema.sql} contains seven tables.

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Table} & \textbf{Purpose} \\
\midrule
player & player data and current Elo \\
opening & ECO opening reference data \\
tournament & tournament metadata and status \\
registration & players registered for tournaments \\
round & rounds belonging to tournaments \\
game & recorded games and results \\
rating\_history & historical Elo values \\
\bottomrule
\end{tabular}
\end{center}

Important integrity rules are enforced in the database itself: primary keys and foreign keys, unique tournament round numbers, a composite registration key, valid game results, distinct White/Black players, and valid tournament status values. Indexes support common lookups for games, registrations and rating history.

\texttt{db/02\_seed.sql} contains deterministic sample data used by CI and must remain compatible with the automated checks.

\section{Backend and Core Logic}
The FastAPI entry point is \texttt{api/app/main.py}. The application provides player, tournament, registration, game, rating-history and standings routes. \texttt{/health} is public; application routes require a valid \texttt{X-API-Key}.

Write operations are transactional. Creating a player also creates its first rating-history row. Creating a tournament creates all round rows. Recording a game inserts the game, updates both Elo values and adds two history rows in one transaction. Errors cause a rollback.

\subsection{Elo}
Elo calculation is isolated in \texttt{api/app/elo.py} with a fixed K-factor of 20.
\begin{verbatim}
E = 1 / (1 + 10^((opponent_rating - rating) / 400))
new = old + round(20 * (actual_score - expected_score))
\end{verbatim}
Ratings are updated immediately after each successfully recorded game.

\subsection{Standings and Buchholz}
Standings are calculated with SQL common table expressions. A win is 1 point, a draw 0.5 and a loss 0. Buchholz is the sum of all opponents' tournament points. Ordering is by points, Buchholz, wins and then player name.

\section{Frontend}
The tkinter frontend contains six tabs: Players, Standings, Rating History, Record Game, Register Player and Create Tournament. \texttt{api\_client.py} is the HTTP client and automatically adds the API key.

After successful writes, refresh callbacks reload dependent views so the user can see new players, tournaments, Elo values and standings without restarting the GUI.

\section{Build, Run and Test}
Create configuration from \texttt{.env.example}. For local Python development:
\begin{verbatim}
python3 -m venv api/.venv
api/.venv/bin/pip install -r api/requirements.txt
api/.venv/bin/pip install -r api/requirements-dev.txt
docker compose up -d postgres
\end{verbatim}
On Linux the local helper can then be used:
\begin{verbatim}
./scripts/run-local.sh
\end{verbatim}

Run API tests with:
\begin{verbatim}
cd api
pytest tests -v
\end{verbatim}

GitHub Actions runs three checks on pushes and pull requests to \texttt{main}: database schema/seed smoke testing, pytest API tests, and LaTeX document compilation.

The Debian frontend package is built on a Debian-based system with:
\begin{verbatim}
sh frontend/debian/build-deb.sh
\end{verbatim}
The generated package is \texttt{frontend/debian/chess-club-manager\_1.0.0\_all.deb}.

\section{How to Add a New Function}
A new feature should follow the existing layers instead of bypassing them. A safe extension workflow is:

\begin{enumerate}
    \item \textbf{Decide whether the database must change.} If new persistent data is needed, update the schema carefully and preserve existing primary keys, foreign keys, checks and indexes.
    \item \textbf{Add or extend a FastAPI route.} Keep validation in Pydantic/backend logic and use the existing database connection helper. Application-data routes should use the API-key dependency.
    \item \textbf{Use transactions for multi-step writes.} If one user action changes several rows, all changes should either succeed together or roll back together.
    \item \textbf{Extend the frontend HTTP client.} Add the required request method in \texttt{api\_client.py} instead of making database calls from the GUI.
    \item \textbf{Add the GUI control or tab.} Keep the tkinter layer focused on user input, messages and displaying API results.
    \item \textbf{Refresh affected views.} Reuse or extend the refresh callback pattern when the new write affects existing read screens.
    \item \textbf{Add automated tests.} Test successful behavior, authentication and important invalid cases. Database changes should also remain compatible with CI schema/seed checks.
    \item \textbf{Run the full test suite and CI.} A feature is not finished until the existing tests still pass.
    \item \textbf{Update documentation.} Describe the new user behavior and any new developer/configuration requirements.
\end{enumerate}

Example: adding a tournament-close feature would likely require a backend route, validation of the current tournament state, a frontend action, API-client method, tests for allowed/disallowed transitions, and documentation. It should not directly modify PostgreSQL from tkinter.

\section{Possible Future Extensions}
With additional development time, reasonable extensions include:
\begin{itemize}
    \item tournament status controls and closing workflow;
    \item edit/delete operations with safe validation;
    \item automatic pairing generation;
    \item richer player statistics and opening analytics;
    \item improved round selection instead of entering raw round IDs;
    \item stronger deployment packaging for macOS and Windows;
    \item user accounts and role-based authorization.
\end{itemize}

These are intentionally outside the delivered scope and should be added only without weakening database integrity or the existing tested workflow.

\section{Developer Checklist}
Before accepting a change, verify that database constraints still hold, API authentication is preserved, multi-row writes are transactional, tests cover the behavior, CI passes, and the manuals/README describe the actual implementation rather than planned features.
